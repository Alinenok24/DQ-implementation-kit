# DQ Implementation Kit

Практический набор для запуска или ревью Data Quality процесса в команде.

Идея простая: Data Quality начинается не с выбора инструмента, а с контракта проверки. Если у проверки нет владельца, severity, failed rows sample и понятного поведения при падении, это еще не DQ-процесс, а просто технический check.

## Что внутри

- [DQ Rule Card](templates/dq-rule-card.md) - шаблон описания одной проверки.
- [Tool Decision Matrix](templates/tool-decision-matrix.md) - как выбрать PyDeequ, Soda, SQL, custom PySpark или генератор.
- [Failed Rows Contract](templates/failed-rows-contract.md) - минимальный стандарт результата для разбора инцидента.
- [DQ Ownership Checklist](checklists/dq-ownership-checklist.md) - что должно быть определено до включения проверки в регулярный контур.
- [LLM-safe Generation Checklist](checklists/llm-safe-generation-checklist.md) - как безопасно использовать LLM для генерации DQ-проверок.
- [Example: Terminated FX Swap](examples/terminated-fx-swap-rule.md) - пример заполненной карточки.

## Как использовать

1. Перед написанием проверки заполните `DQ Rule Card`.
2. По `Tool Decision Matrix` выберите место и способ реализации.
3. Зафиксируйте `Failed Rows Contract`, чтобы падение проверки было разборным.
4. Проверьте ownership: кто владеет правилом, кто реагирует, что происходит с pipeline.
5. Если проверка генерируется через LLM, пройдите LLM-safe checklist.

## Минимальный стандарт DQ-проверки

Каждая production DQ-проверка должна отвечать на 7 вопросов:

| Вопрос | Зачем |
|---|---|
| Что защищаем? | Чтобы check был связан с бизнес-риском, а не только с полем в таблице |
| Где запускаем? | Чтобы ошибка ловилась в правильном месте пайплайна |
| Кто владеет правилом? | Чтобы было понятно, кто принимает изменения и разбирает падения |
| Какой severity? | Чтобы отличать блокирующие ошибки от мониторинга |
| Что возвращаем в failed rows? | Чтобы можно было быстро найти root cause |
| Что происходит при падении? | Чтобы check влиял на процесс, а не просто писал лог |
| Где хранится история? | Чтобы результат был воспроизводимым и аудируемым |

## Быстрая формула выбора инструмента

| Ситуация | Подход |
|---|---|
| Ошибка возникает внутри конкретной трансформации | Локальный gate рядом с расчетом: PyDeequ или custom PySpark |
| Правило должны читать аналитики и доменные владельцы | Декларативный DQ contract / Soda YAML |
| Нужен единый мониторинг по витринам | Платформенный DQ-сервис |
| Нужны samples невалидных строк для разбора | Failed Rows Contract обязателен независимо от инструмента |
| Правил становится слишком много для ручного сопровождения | Генератор проверок на основе metadata, samples и feedback loop |

## Главный takeaway

Не пытайтесь сразу выбрать один лучший DQ-инструмент.

Сначала опишите проверку как контракт:

- бизнес-смысл;
- слой данных и источник;
- условие падения;
- severity;
- failed rows sample;
- owner и SLA реакции;
- поведение pipeline при падении.

И только потом выбирайте реализацию: PyDeequ, Soda, SQL, custom PySpark или генератор.
