# Tool Decision Matrix

Используйте эту матрицу, чтобы выбрать место и способ реализации DQ-проверки.

## Быстрое решение

| Вопрос | Если да | Тогда |
|---|---|---|
| Ошибка возникает внутри конкретной трансформации? | Да | Локальный check рядом с расчетом |
| Нужно поймать проблему сразу после join / agg / step N? | Да | PyDeequ или custom PySpark gate |
| Правило должны читать аналитики? | Да | Декларативный формат: Soda YAML или DQ contract |
| Проверка нужна на многих витринах? | Да | Платформенный DQ-сервис |
| Нужен единый мониторинг и алерты? | Да | Soda + Grafana / messenger alerts |
| Нужно видеть failed rows? | Да | Failed Rows Contract обязателен |
| Падение должно остановить выпуск? | Да | Gating в pipeline |
| Правил становится слишком много? | Да | Генератор проверок + templates |
| Есть риск галлюцинаций LLM? | Да | Metadata + samples + test run + feedback loop |
| Нужна воспроизводимость? | Да | runId, prompt, model response, artifacts, logs |

## Сравнение подходов

| Критерий | PyDeequ / custom PySpark | Soda Core | Generated checks |
|---|---|---|---|
| Идеальный сценарий | Локальные гейты на критичных шагах расчета | Платформенный DQ-сервис и единый контроль витрин | Массовое создание похожих проверок |
| Лучшее место в потоке | Рядом с трансформациями | После публикации витрины / таблицы | После описания правила и источников |
| Читаемость для аналитика | Средняя: это код | Высокая: декларативные checks | Высокая, если есть DQ Rule Card |
| Кастомная логика | Максимальная гибкость | Хорошо для типовых и SQL-based проверок | Зависит от контекста и тестового запуска |
| Мониторинг | Нужно собирать отдельно | Единый обзор проще | Нужна интеграция с run history |
| Root cause | Хорошо, если check рядом с шагом трансформации | Видно какой check упал, глубина требует анализа | Хорошо, если сохраняются logs и failed rows |
| Риск | Проверки расползаются по коду | Checks не влияют на выпуск данных | Галлюцинации без metadata и tests |
| Как лечится | Гайдлайны, общий формат метрик, переиспользование | Gating, ownership, SLA на реакции | Feedback loop, schema, samples, audit trail |

## Правило выбора

Не выбирайте инструмент по популярности.

Выбирайте по месту, где ошибка должна быть поймана:

- **внутри расчета** - PyDeequ / custom PySpark;
- **на уровне опубликованной витрины** - Soda Core / SQL checks;
- **на уровне массового покрытия однотипными правилами** - generator + templates;
- **на уровне расследования инцидентов** - failed rows sample + logs + owner.
