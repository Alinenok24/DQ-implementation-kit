| Критерий | PyDeequ | Soda Core |
|---|---|---|
| Идеальный сценарий | Локальные гейты на критичных шагах расчёта | Платформенный DQ-сервис: стандарты, прозрачность, мониторинг |
| Лучшее место в потоке | Рядом с трансформациями: после join / agg / step N | После публикации витрины или таблицы |
| Где живут правила | В репозитории и коде конкретного расчёта | В централизованных checks / стандартах |
| Читаемость и ревью | Средняя: это код | Высокая: декларативная спецификация |
| Кастомные доменные правила | Очень сильный: можно выразить любую PySpark-логику | Хорош для типовых checks и SQL-based правил, сложный кастом дороже |
| Масштабирование на много витрин | Дороже при росте числа мест поддержки | Проще тиражировать как единый DQ-контур |
| Парадигма | DQ as code | DQ as declaration / config |
| Статистика и профилирование | Сильная сторона: метрики и аномалии | Чаще декларативные пороги и регулярный контроль |
| Риск / антипаттерн | Проверки расползлись по коду, нет единого обзора | Checks есть, но не влияют на выпуск данных, нет gating |
| Как лечится | Гайдлайны, общий формат метрик/логов, переиспользование | Связать с пайплайном, определить ownership и SLA на реакции |
| Ownership | Владельцы обычно команда разработки расчётов | Платформа поддерживает контур, домены владеют правилами |
| Алертинг и реакции | Интеграции руками через оркестратор/инциденты | Проще настроить уровни алертов после прогона |
| Мониторинг / витрина результатов | Нужно собирать самим | Проще сделать единый обзор, хорошо ложится на Grafana |
| Root cause | Быстро, если диагностика рядом с шагом трансформации | Видно, какой check упал, но глубина часто уходит в анализ данных |
| Стоимость вычислений | Можно оптимизировать внутри job | Отдельный scan, нагрузку надо планировать |
| Переиспользование правил | Через модули/функции, нужна дисциплина | Через единые стандарты и наборы checks |
